# Changelog

This file owns the release history for `django-lux`.

> `django-lux` is the renamed, actively-maintained successor to
> [`django-microsys`](https://github.com/debeski/django-microsys) (now archived).
> Release history prior to v1.0.0 lives in that archived repository.

## v1.2.14

- **Public Root Theme Now Uses The Theme Swatch Picker**: The Settings → Security **Public root theme** field is no longer a searchable card dropdown — it reuses the theme picker's visual swatches by binding to `DluxChoiceSelectorWidget(variant='swatch', …)` with each theme's `dlux-theme-preview--<slug>` swatch as the option `preview_class`. The optional "use system default" stays as the empty choice (a `bi-circle-half` glyph), and the list is limited to the **allowed themes** (`get_theme_options(s, config.get('allowed_themes'))`), matching the default-theme picker. Server-rendered radio group — no new JS/CSS (the `--swatch` variant already exists in `selectors.css`); `clean_public_root_theme` still accepts any stored slug so restricting the allowed set can't block a save. forms.py only; no migrations; inline-safe.
- **Reset Defaults Moved To A Footer Danger Zone**: The "Reset Defaults" control no longer sits as a drag-reorderable card *among* the preference cards it wipes. It's now a standalone full-width danger strip (`.dlux-options-reset-footer` / `.dlux-options-reset-bar`) rendered below the options grid — title + description on the start side, the Reset → Confirm/Cancel actions on the end side, with the red `.dlux-options-panel--danger` accent as the danger cue. The swap between the Reset trigger and the inline Confirm/Cancel now animates (a small fade + slide-in via `@starting-style`, with `prefers-reduced-motion` and old-browser fallbacks degrading to an instant swap). No JS change: `initResetDefaults` still binds by the global `.dlux-options-panel--danger[data-reset-url]` selector and the same `#btnReset*` / `#resetActions` IDs. Template/CSS only; no migrations; inline-safe.
- **Combined Admin Panel On The Options Page**: The three admin-only Options cards (System Info, Backup & Restore, System Settings) are merged into one pinned, full-width **Admin Panel** card that always occupies the first row (`.dlux-admin-panel-card { grid-column: 1 / -1 }`, excluded from the drag-reorder so it stays first). Its top zone holds three flex tiles that expand/shrink with width and wrap only when forced — **System status** (storage gauge + server time + Python/Django inline, with the rest of the diagnostics — OS, decrypter, DRF, API/DB/cache/email/tasks — behind a `<details>` "More system details" expander), **Update** (the inline `.dlux-updater` widget pulled out of the old info table), and **Backup** (summary + open). The System Settings tiles now form a horizontal auto-fill grid (`.dlux-admin-settings-grid`) across the full bottom strip instead of a cramped 2-column card. Any future admin-only option goes in this panel. New `admin_panel_title` / `admin_panel_desc` / `admin_panel_more_details` strings (en + ar); theme-aware sub-tile backgrounds for dark/retro/gothic/prism/neon. The show-titlebar/show-sidebar-on-public toggles remain under Settings → Security (revealed when Public Root is enabled). Template/CSS only; no migrations; inline-safe.
- **Per-User Modal Size Now Reliably Drives The Dynamic Modal Width**: The Options → **Modal Size** (and Form Density) per-user preference was being overridden by the global admin default. Two causes, both fixed. (1) The System Settings live preview (`applyLayoutBodyPreview` in `system_setup.js`) wrote the admin-default `default_modal_size` / `default_form_density` onto the editing admin's own `data-dlux-modal-size` / `data-dlux-form-density` body attributes every time the settings modal loaded — so after the settings modal opened, every dialog snapped to the global default (the "loads at the right width, then reverts once loaded" symptom). Those two are the *defaults for non-overriding users*, not a live body preview, so they are no longer previewed; only the genuinely global `sticky_table_headers` / `zebra_striping` still preview live. (2) The shared dynamic modal now re-asserts the viewer's active `modal_size` (from `window.USER_PREFS`) onto the body attribute right before `show()`, so each dialog opens at the correct width from the first frame instead of inheriting a stale `data-dlux-modal-size` left by a previous modal or a settings preview. Frontend-only; no migrations; inline-safe.
- **Admin Notification When DjangoLux Is Updated**: A successful inline update now posts an in-app notification to every active superuser ("DjangoLux was updated to version X.Y.Z"), linking to Options. `UpdateService._complete()` fires it for `apply` runs that reach `completed`, after the run is durably committed — fully isolated (a notification failure can never affect the update lifecycle) and only when notifications are enabled. New `notif_app_updated_title` / `notif_app_updated_message` strings (en + ar).
- **Sidebar/Landing Discovery No Longer Lists API Endpoints (Duplicate Entries Fix)**: Auto-discovery surfaced the API counterparts of page views — e.g. `documents_api:decree_list` → `/api/decrees/` alongside `documents:decree_list` → `/documents/decrees/` — which share the same inferred label, so the per-user **Landing page** picker (and the sidebar entry catalog) showed each discovered model twice (internal dlux items, with a single URL each, were unaffected). `_is_candidate` now excludes the `<app>_api` / `api` URL namespace convention and `/api/` paths (the broader `/api/` path part replaces the narrower `/sys/api/`), so only the navigable page view is offered. Verified against the live decrees project (11 → 8 options, no duplicate labels).

## v1.2.13

- **Sticky Header + Zebra Striping Toggles, Form Density, And Modal Size (Layout Settings)**: *System Settings → Themes & Typography* gained four new `layout_config` controls (all `legacy_flat`, no migration). **Sticky table headers** (`sticky_table_headers`, default on) and **Zebra striping** (`zebra_striping`, default on) now gate what were previously unconditional `tables.css` rules — the sticky-`thead` block and the `nth-child` row shading are scoped under `body[data-dlux-sticky-header="on"]` / `body[data-dlux-zebra="on"]`, emitted from `base.html`. **Default Form Density** (`default_form_density`, dense/balanced/roomy, default balanced) is independent of table density and drives new `--dlux-form-*` CSS variables in `form_fields.css` via `body[data-dlux-form-density]` (gutter, label margin, input/textarea min-height). **Default Modal Size** (`default_modal_size`, compact/standard/wide, default standard) maps to a dialog class (`modal-lg` / `modal-xl` / `modal-xl dlux-modal-wide`) computed as `APP_CONFIG.appearance.modal_size_class` and applied to the shared `dynamic_modal.html`; `wide` widens past `modal-xl` on ≥1200px. All four are surfaced under `APP_CONFIG.appearance.*`, round-trip through export/import, gated behind `_should_apply_db_override`, and have single-step-save preservation. The Form Density and Modal Size pickers render with the shared `DluxChoiceSelectorWidget` (toggle variant, icon + translated description per option) — matching every other choice control in the settings form rather than a bare `<select>` — and the public-root theme picker uses the searchable `card` variant. **Form Density and Modal Size are also per-user overridable**: both gained an Options-panel card (mirroring Table Density — preview partial + `options.js` handler → `/sys/api/preferences/update/` validates `form_density`/`modal_size` → resolved in `dlux_context` → applied via the `data-dlux-form-density` / `data-dlux-modal-size` body attributes). Modal width is now driven by `body[data-dlux-modal-size]` CSS (compact ~800px / standard ~1140px / wide ~min(96vw,1480px)) instead of a Bootstrap dialog class, so it resolves per-user and previews live. Form density was made genuinely distinct — the density vars now also drive the inter-row margin (overriding crispy's fixed `mb-3`) and input padding, so dense/balanced/roomy produce clearly different field heights and gaps. The body-affecting settings (footer show/hide + text, sticky headers, zebra striping, form density, modal size) now **live-preview** in the settings modal via `applyImmediateSystemSettingsPreview`; public-root-only settings are excluded (like language). **Sticky headers now actually work**: the data table sits inside `overflow:hidden`/`overflow-x:auto` wrappers that trapped `position:sticky`; when sticky is on those wrappers are set to `overflow:visible` (corners kept via the per-cell radii) so the header pins to the top of `#mainContent` on page scroll. Because `#mainContent` carries `p-4` (1.5rem) padding, the stuck header uses `top: -1.5rem` so it pins **flush under the titlebar** rather than leaving a see-through 1.5rem strip (the padding) where rows would scroll through. The stuck header is also forced **solid** (an opaque `--table-row` backdrop composited under the themed header gradient — selector `.dlux-data-table.table` so it beats the dark-family/mono themes' own `!important` header rules) so the scrolling rows don't bleed through the glass surface. Trade-off: wide tables lose the contained horizontal scrollbar when sticky-on.
- **Registration Honeypot Toggle**: The registration form's long-standing hidden `website` bot-trap is now switchable from *System Settings → Security* via `registration_config.honeypot_enabled` (default on). The `register_view` bounce (`request.POST.get('website')` → `register_sent`) is now gated on `public_registration_config()['honeypot_enabled']`, so admins can disable the trap (e.g. before swapping in CAPTCHA) without code changes. Exposed as `APP_CONFIG.security.honeypot_enabled`.
- **Fixed Public-Root Theme + SEO Title/Meta (Public Root Settings)**: `public_root_config` gained a **Public root theme** (`public_root_theme`, default ''=inherit) that forces an admin-chosen theme for anonymous visitors on the public root — `dlux_context` overrides the active theme and ensures the theme's stylesheet is emitted even if it is outside the normally-allowed set. Added optional **Public root page title** (`public_root_title`) and **Public root meta description** (`public_root_meta_description`, length-bounded) that `base.html` emits as `<title>` / `<meta name="description">` only for the anonymous public index. All three are `legacy_flat`, surfaced under `APP_CONFIG.security.*`, and round-trip through export/import.
- **Centralized Public-Root Chrome: `show_titlebar_on_public` + `show_sidebar_on_public`**: Titlebar and sidebar visibility on the public root is now controlled by two inverted-polarity toggles in `public_root_config` (both default **off** = hidden), replacing the titlebar-specific `titlebar_config.hide_on_public_unauthenticated_index` (its form field on the Titlebar step is removed) and the hardcoded `{% if request.user.is_authenticated %}` sidebar gate in `base.html`. A new shared `_is_public_index()` helper in `context_processors.py` drives `hide_titlebar_for_public_index`, the new `dlux_show_sidebar` flag (authenticated **or** anonymous-public-root-with-sidebar), the public theme/title/meta overrides, and `dlux_is_public_index`. Legacy data and `DLUX_CONFIG`/import payloads carrying `hide_on_public_unauthenticated_index` migrate (inverted) to `show_titlebar_on_public` across the settings, DB, and import layers, and `SystemSettings.load()` first-run seeding now mirrors all the new keys so the auto-created singleton no longer clobbers a `DLUX_CONFIG` override during config expansion.
- **Updater Recovery Hardening: Self-Healing Reconcile + Unified Baked-Version Source**: Fixed two latent runtime-supervisor bugs in `dlux/updater`. (1) **Reconcile no longer wedges into a permanent `degraded` state.** When the recorded active release can no longer be served and *cannot be rebuilt* — no staged volume release on disk and no downloadable wheel (an image/mount activation, a backward image move, or a wiped runtime volume) — `UpdateService.reconcile()` now reverts to the baked image (re-activates it, resets stale active/previous/latest metadata, bumps generation, restarts the worker) instead of hard-failing by chasing a wheel that never existed. And once the runtime has converged back onto the baked image (`active == baked`), a lingering `degraded` flag from a transient failure is now cleared, so a one-off degrade self-heals on the next reconcile instead of sticking forever (`degraded`s tied to a *present volume release* — e.g. a failed-rollback target — deliberately stay sticky for operator review). The duplicated baked-image reset is consolidated into a shared `_reset_to_baked_image()` helper. (2) **The scaffold runtime supervisor now derives `DLUX_BAKED_VERSION` from `dlux.__version__`** (the running code's release manifest) instead of `importlib.metadata.version("django-lux")`, falling back to package metadata only when `dlux` can't be imported. This makes bind-mounted source-checkout dev "just work" (where installed-package metadata is absent or stale) and unifies the version source of truth with `get_baked_version()`, which already preferred `__version__`. Note: the supervisor script lives in the generated project's `tools/`, so existing deployments pick up the version-source fix on the next rebuild / `enable-updater` re-copy; the reconcile fix ships inside the `dlux` package and applies inline. A row already stuck at `degraded=t` clears on the first reconcile after upgrade (or via a one-time flag clear / `down -v`).
- **`scan_link/main.js` Is Now Re-Execution-Safe (`ScanLinkError` Console Error)**: `scan_link/js/main.js` declared `class ScanLinkError` and `class ScanLink` at top level, so if the file was ever loaded/executed twice in the same page — a project-level `custom_scripts` include, an AJAX fragment that re-runs it, or a stale/duplicated static copy left behind when switching package versions — the second run threw `Uncaught SyntaxError: Identifier 'ScanLinkError' has already been declared`. Both are now declared as `var X = window.X || class X {…}`, which is redeclaration-safe and reuses the existing global on a second load (the `window.ScanLink`/`window.ScanLinkError` exports are unchanged, and `scan_button.js` already runs in an IIFE). Verified in a real browser: a forced second load of the file is now a clean no-op with zero console errors. The `scan_link` scripts also gained an explicit `?v=` cache-bust (they previously had none, which is how a stale copy could persist across upgrades).
- **Fixed Blank System Settings Steps After Security (Literal `<title>` In Help Text)**: The new `public_root_title` field's help string contained a literal `<title>` HTML tag. crispy renders form help text as raw HTML, so when the dynamic-modal AJAX form was injected via `innerHTML`, the browser's HTML parser treated that `<title>` as a real element and swallowed all sibling markup after it — i.e. every wizard step rendered *after* the Security step (Login, Sidebar, Nav Bar, Titlebar, Notifications, Themes, Logging, Profile, Backups). The result was steps 3–11 silently vanishing from the DOM with **no Python or JavaScript error** — only steps 0–2 survived. The help text (en + ar, plus the form fallback) no longer embeds raw tags. Verified end-to-end in a real headless browser: every single-step modal now injects all 12 wizard steps with the correct one visible.

## v1.2.12

- **`dlux_setup` No Longer Duplicates The Settings Block (AST Detection)**: The `dlux_setup` management command's "is the helper already in settings.py?" check (`_ensure_settings_block`) matched the literal line `from dlux.utils import dlux_settings`. But a scaffolded project's `settings.py` imports it **combined** — `from dlux.utils import get_secret, dlux_settings` — which doesn't contain that exact substring, so re-running `dlux_setup` failed to detect the existing wiring and **appended a second `dlux_settings(globals())` block**. The check now parses the AST (`_settings_block_present`): it confirms `dlux_settings` is imported *from* `dlux.utils` (handling combined, reordered, aliased `as`, and multi-line imports) **and** actually called, falling back to a literal check only when the file can't be parsed. Same-named imports from other modules are correctly ignored. New `dlux/tests/test_dlux_setup.py` covers all import styles.
- **Footer Sits Behind The Sidebar (z-index Fix) + Theme-Aware Colors**: The global footer was painting over the bottom of the expanded sidebar because it used `z-index: 1020` while the sidebar is `z-index: 900`. The footer — a faint background strip — now uses `z-index: var(--dlux-footer-z, 850)`, so it stays below the sidebar (sticky desktop / fixed `1000` mobile), navbar/titlebar, and Bootstrap modals/offcanvas, while still painting above static page content. The expanded sidebar now correctly renders in front of the footer. Its default colors are also no longer a hardcoded white bar (which looked wrong on dark-based themes): the background/text/border now derive from the active theme tokens via `color-mix` — `--hbody` for the translucent surface, `--htitle`/`--title` for text and border — so the strip flips correctly across all themes (dark, aether, gothic, neon, prism, retro, mono) with no per-theme overrides. `--dlux-footer-bg` / `--dlux-footer-color` / `--dlux-footer-border` remain overridable.
- **Footer Can Be Disabled + Optional Footer Link (System Settings)**: The footer is now genuinely controllable from *System Settings → Themes & Typography → Footer*. A new **Show page footer** toggle (`layout_config.footer_enabled`, default on) hides the built-in footer entirely when off — previously a blank Footer text just fell back to the default `© year · name` line, so there was no way to remove it. A dev `custom_footer.html`/`footer` block still always renders (explicit code overrides the toggle). Also added an optional **Footer link text** + **Footer link URL** pair: the URL is scheme-validated server-side in `normalize_layout_config` (only `http(s)://`, `mailto:`, or a root-relative `/path`; `javascript:`/`data:`/protocol-relative dropped), so a blank or invalid URL simply renders no link, and the label falls back to the URL. All three new fields are `legacy_flat` layout-config keys (no migration), declared on `SystemSettingsForm` with single-step-save preservation (`clean_footer_enabled` keyed on the Themes step index; `clean_footer_link_*` preserve omitted values), surfaced as `APP_CONFIG.appearance.*`, and round-trip through export/import. New `form_sys_footer_enabled`/`help_sys_footer_enabled`/`form_sys_footer_link_text`/`form_sys_footer_link_url` strings (en + ar). Fixed an attendant bug in the just-moved `allow_user_home_url` toggle: a single-step modal save of another step would have wiped it — it now has the same step-keyed preservation (`clean_allow_user_home_url`).
- **"Allow Users To Set Their Landing Page" Moved To Step 3 (Security)**: The per-user home-URL override (`profile_config.allow_user_home_url`) is no longer buried in the Step 11 *Profile Page* builder — it now appears as a standalone toggle directly beneath the **Home URL** field in Step 3, where it belongs (it governs whether users can override that Home URL). Storage is unchanged (still `profile_config.allow_user_home_url`, same normalizer/consumer): the form declares an `allow_user_home_url` `BooleanField`, seeds it from the stored config, renders it via `build_settings_toggle_field` next to `home_url`, and folds its value back into `profile_config` on `clean()`. New `help_sys_allow_user_home_url` help string (en + ar); the existing `profile_allow_user_home_url` label is reused.
- **Inline Updater UX: Clear Success State, Honest Status, Spinning Check Button**: Fixed several confusing moments in the Options → DjangoLux updater (`dlux/static/dlux/main/js/updater.js` + `dlux/templates/dlux/includes/options.html`). (1) After a successful apply/rollback the progress modal used to leave only a disabled-then-enabled **Cancel** button, so a successful update felt unfinished — the dismiss button now becomes a green **Finish** (`dlux_update_finish`) on `completed`/`rolled_back`, alongside the already-green 100% bar, and resets to Cancel when the review modal reopens. (2) Removed the misleading root run-status line that read *"Update operation in progress"* during a mere **check** and then *"Update operation completed"* afterward (it implied an update had run); the completion toast is now gated to real `apply`/`rollback` actions only. (3) The **Check for updates** button now spins via the shared `DluxLoadingButton` while a check is in flight instead of relying on that status line. (4) The remaining status line is derived and translated client-side from state — *Ready for inline update* (`dlux_update_ready`), the new *DjangoLux is up to date* (`dlux_update_up_to_date`), or the backend reason — rather than echoing a raw value. New `dlux_update_finish` / `dlux_update_up_to_date` strings (en + ar) and `data-label-finish` / `data-label-uptodate` root attributes.
- **Loading Button Preserves The Host Button's Layout While Spinning**: The `DluxLoadingButton` busy state no longer force-centers content. In the default (no-label) mode it now works **in place**: it swaps a button's leading icon for the spinner — keeping that icon's position and margin classes (e.g. dlux's `<i class="bi bi-save text-light me-1 h4">`) — and leaves the text untouched, so dlux's icon-beside-text submit buttons keep their design while loading instead of collapsing to a centered spinner+text. Buttons with no icon just get a small leading spinner. Content-replace mode (an explicit `label`, and task-polling which streams status text) is unchanged. The CSS no longer overrides the button's `display`/alignment.
- **Reusable Loading Button Helper (`DluxLoadingButton`) With Spinner + Task Polling**: Added one shared spinner-in-button primitive (`dlux/helpers/loading_button/js/main.js` + `css/main.css`, loaded globally from `dlux/base.html`) to replace the ~7 bespoke disable/spinner/restore reimplementations scattered across login, scan, dynamic-modal, updater, and 2FA code. It exposes `window.DluxLoadingButton` with four usage modes: a **promise API** (`run(btn, asyncFn)` / low-level `start(btn) -> handle` with `update/done/error/stop`) for project JS; a **declarative submit spinner** (`data-dlux-loading` on a submit button, cooperating with `prevent_double_submit`); a **declarative task-polling** button (`data-dlux-loading-start` POST + `data-dlux-loading-poll`) that CSRF-POSTs to kick off a server task then polls a `{status, progress, message, redirect, error}` JSON contract until a terminal status — generalizing the existing scan/updater poll loops; and a **custom-event** mode (`data-dlux-loading-event`) that hands a listener the live handle. Sets `aria-busy`/`aria-disabled`, swaps contents for a Bootstrap `spinner-border-sm`, restores on completion with an optional done/error affordance and minimum-duration anti-flash, and fires bubbling `dlux:loading:start|poll|done|error` events. Labels fall back to new `DLUX_STRINGS.loading_failed` / `loading_timeout` (reusing existing `loading`), overridable per button via `data-dlux-loading-*`. External assets + CSP nonce per DSRP-1. Migrated the first two call sites onto it: the **login/register submit buttons** now carry `data-dlux-loading` (the bespoke spinner block in `login.js` was removed, and the helper's submit handler gained an HTML5 `checkValidity()` guard to match the old behavior), and the **dynamic modal's AJAX form submit** (`dynamic_modal/js/main.js`) now drives the spinner through a `start()` handle instead of toggling `disabled` by hand (restoring only on real errors; validation re-renders and navigations discard the busy button as before). Remaining call sites (scan, updater, 2FA) still work unchanged and can migrate opportunistically. Documented in the customization guide.

## v1.2.11

- **Scaffold Nginx Config Is Now an `envsubst` Template (Parameterized Host + Upload Ceiling)**: Generated projects ship the reverse-proxy config as `.nginx/default.conf.template` mounted into the official nginx image's `/etc/nginx/templates/` directory, so nginx renders it at container start (writing `/etc/nginx/conf.d/default.conf`) with `server_name ${NGINX_SERVER_NAME}` and `client_max_body_size ${NGINX_MAX_SIZE}` filled from the environment (compose defaults `localhost` / `10M`, overridable in `.secrets/.env`). `NGINX_ENVSUBST_FILTER: "NGINX_"` is set so substitution is restricted to `NGINX_*` vars and nginx's own runtime variables (`$host`, `$remote_addr`, `$scheme`, …) survive. Completed the wiring the in-progress edit had left dangling: `dlux/scaffold.py` mapped the source to `.nginx/nginx.conf` while `compose.yml.tmpl` mounted `.nginx/default.conf.template` — they would never have matched, leaving nginx with no server block. The scaffold source is renamed `default.conf.template.tmpl` (the file is legitimately a template-within-a-template: nginx `.template` inside the scaffold's `.tmpl`); the old `nginx.conf.tmpl` is relocated under `.xpose/`. Updated the generated `README.md` and `test_scaffold.py` to the new filename/mount/`NGINX_*` env assertions. The `enable-updater` legacy-migration path still targets the old `.nginx/nginx.conf` because it upgrades pre-existing projects generated with the previous layout. Also fixed an adjacent typo in the same compose hunk where `POSTGRES_DB` had become the literal `"${POSTGRES_DB:-project_slug}"` (dropping `{{ project_slug }}` and `_db`); restored to `"${POSTGRES_DB:-{{ project_slug }}_db}"` so each project keeps its own default DB name while staying overridable.
- **Delegatable Record Deletion (Re-enabled `delete_<model>` Permission + Permission-Gated Context Menu)**: `delete_<model>` permissions are now assignable from the grouped permission UI — `get_assignable_permissions_queryset()` (`dlux/forms.py`) previously excluded every `delete_*` codename via a `codename__regex=r'^(delete_)'` clause, so only superusers could ever delete; that clause is removed. Sensitive deletes stay excluded by the existing clauses (the `auth` user/group/permission models and non-whitelisted internal `dlux` models such as activity logs, scopes, and system settings; the `section` model remains the documented exception governed by `manage_sections`). The grant is the single control point for both surfaces: it reveals the **Delete** entry in a table row's right-click/long-press context menu (built in `dlux/tables.py` / `dlux/patches.py` with `permissions: ['<app>.delete_<model>']`) and authorizes the backend delete view (which independently returns 403 without the permission). Closed a DSRP-1 UI/authorization gap in `filter_context_actions` (`dlux/utils/crud.py`): the `manage_sections` override used to grant **all** permissioned actions, so a `manage_sections` holder saw Delete on data grids they could not delete; it now only overrides actions explicitly flagged `section_action: True` and never bypasses per-model delete/change permissions. New tests in `dlux/tests/test_permissions_ui.py` cover assignable-delete exposure (with sensitive-delete exclusion) and the context-menu delete gating (including the `manage_sections` non-bypass). Docs: admin-guide permission-assignment section + `docs/security-dsrp-1.md`.
- **Reusable Global Footer (Copyright/Credit Strip) + Admin-Editable Footer Text**: Added a dedicated, faint footer that base templates render on every page — a `dlux/includes/footer.html` partial pinned to the bottom of the viewport via `dlux/main/css/footer.css` and emitted from a new `{% block footer %}` in `dlux/base.html`. It is very small (`0.68rem`), light/muted (`--dlux-footer-color`, theme-aware via `color-mix` on `--htitle`), and semi-transparent with a backdrop blur (`--dlux-footer-bg: rgba(255,255,255,0.42)` + `backdrop-filter: blur(6px)`); `pointer-events:none` on the bar (re-enabled on links/buttons) so it never blocks content clicks, `z-index:1020` so Bootstrap modals/offcanvas stay above it, and `:empty` collapses it. The footer text is now a **runtime System Settings layout option**: a new `footer_text` field on the `layout` settings group (`dlux/system/schema.py`, `legacy_flat=True`) stored in `SystemSettings.layout_config` — no migration, since the `legacy_flat` registry auto-creates the `layout_config`-backed model property and `apply_system_settings_import` persists it. It is edited from *System Settings → Themes & Typography → Footer* (new `footer_text` `CharField`, max 300 chars, with single-step-safe `clean_footer_text` preservation), normalized/capped in `normalize_layout_config` (`LAYOUT_FOOTER_TEXT_MAX_LENGTH`), surfaced as `APP_CONFIG.appearance.footer_text` via `build_config_groups`, and round-trips through flat export/import (`SYSTEM_SETTINGS_EXPORT_FIELDS`).
